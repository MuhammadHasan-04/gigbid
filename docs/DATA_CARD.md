# Data card

GigBid uses two kinds of data, and every job, client and market number says which one it is (`source: "real"` or
`source: "synthetic"`; the UI shows a **real post** / **synthetic** badge).

* **Synthetic** (Part 1): the GigSim stand-in world, built because the instructor GigSim, persona corpora and dev set
  were not available. It has gold labels (bid/skip, scams, injections, fair price bands, relevant evidence), so every
  headline metric is computed on it.
* **Real** (Part 2): six Kaggle datasets the course allowed on 11 Nov. Real posts have no gold labels, so they are used
  for a realistic job board and market prices, and to test where the synthetic world and the rules are wrong.

# Part 1 – Synthetic data

## Provenance

Everything in this part is generated by `gigsim/generate.py` (seeded, reproducible: `make seed`). It is synthetic and may
be shown publicly. It contains no real people, clients or Upwork data. The three freelancer personas and their portfolios
are synthetic in every configuration; no real freelancer's work is used.

| Artefact | Size | Notes |
|---|---|---|
| Personas | 3 (AI/ML, full-stack, data analyst) | each: CV (PDF), 22 projects → 22 Markdown case studies, ~15 repos (README + code), ~11 reviews, 150 past proposals labelled won / replied / ignored by the simulated-client model |
| Clients | 260 | 16% risky (unverified, no spend, bad reviews); hidden preferences: dislike of generic openings, concise preference, budget flex, base reply propensity |
| Historical jobs | 1,500 | awarded prices for market statistics |
| Dev set | 600 jobs (200 / persona) | 62% in-domain, 18% adjacent persona, 20% out-of-domain; 12% scams (1–2 signals), 7% planted prompt injections; gold: bid/skip with reasons, scam kinds, relevant projects with graded relevance, fair price band (p30–p75 of comparable history) |
| Live stream | 158 jobs | released over simulated time; 10% reposted duplicates |
| Held-out | 180 jobs (60 / persona) | different seed, git-ignored, used only for the final run |

## Built to defeat naive RAG

The same project is described three ways: a business-language case study where about half the skills appear only as
paraphrases ("a background task queue" for Celery), a technical README, and a terse CV line. One skill per repo is visible
only in the code (imports), not in the README. Retrieval units are projects, so gold relevance counts any item about the
project.

## Known biases and threats to validity

* **Same author for generator and system.** The rule-based (heuristic) decision logic mirrors the generator's labelling rules, which inflates heuristic bid-or-skip F1. Treat those numbers as an upper bound for rules, not a fair comparison with the model profiles.
* The skill extractor only matches canonical names, never the generator's alias list, so aliases are not leaked into retrieval. The verifier does use the alias ontology (it is the product's skill vocabulary).
* Simulated clients are a logistic model over observable proposal features, so "reply rate" measures what that model rewards (evidence for must-haves, no generic opening, price under ceiling, no fabrication). It is a proxy, not ground truth.
* Small vocabulary: 86 skills, 12 industries, 29 archetypes.

## Decision: what retrieval ships (B)

The hypothesis, stated before running: *"Requirement decomposition plus hybrid retrieval raises evidence Recall@5 by 5+
points over V0 on jobs with 4+ requirements."* **Rejected.** On the heuristic profile, V1 (decomposition) and V2
(hybrid) on their own *lowered* Recall@5 slightly (0.7488 and 0.7296 vs 0.7583).

I then ran a 64-configuration grid over the switches (`rag_sweep_heuristic.json`), with nDCG@10 declared as the primary metric
before running. The winner was **decompose + hybrid + contextual line + structural chunks**: nDCG@10 0.8799 vs V0 0.8333 on dev,
and 0.8634 vs 0.8394 on held-out. That is what ships (`rag/variants/__init__.py`, `rag.variant: best`). The runner-up
(dense instead of hybrid) has a 0.0025 lower nDCG but a 0.04 higher Recall@5. That gap is within noise, and I kept the
pre-declared rule rather than switching after seeing the results. The ablation (`rag_heuristic.json`) shows the contextual line
and structural chunks carry most of the gain. Multi-vector aggregation *hurts* when combined (MRR 0.9894 → 0.9232).

V3 (cross-encoder bge-reranker-v2-m3) could not run: the weights are on Hugging Face, which this workspace could not
reach. The code path exists (`rerank: bge`), and an LLM pointwise reranker (`rerank: llm`) is the alternative.

Retrieval vs outcome: shipped 0.8803, V5 0.8761, V8 0.8604, V0 0.8347 simulated reply rate (scam rules v2; with v1 the
numbers were 0.8793 / 0.875 / 0.8591 / 0.8333). The ordering roughly follows nDCG, but the spread (about 0.05) is smaller than the effect of one verifier rule (see `docs/WRITEUP.md`).

Combined this way, the 60k posts supply realistic jobs, the 1.3M contracts supply prices (posts only state budgets, contracts
show what was actually paid), and the 2024 sets supply recency and an untouched sample for testing.

## Preprocessing (`scripts/ingest_kaggle.py`, deterministic, ~75 s)

1. **Download** with `kagglehub` (cached). Raw files are **not committed**; `data/real/MANIFEST.json` records each file's size and SHA-256.
2. **Job posts (60k)**: drop rows with no title or a description under 150 characters; de-duplicate by URL and by identical
   description (63,950 → 50,209).
3. **Personal data**: emails, links and phone numbers in descriptions become `[email removed]` / `[link removed]` /
   `[phone removed]` (144 of 1,295 kept posts had one). Client records keep only aggregate public stats; there are no
   client names or ids in the source.
4. **Category mapping** to GigBid's 21 categories (`categorize()`): first the title and the client's own skill tags; a post
   whose tags are all outside the three personas' markets is `out_of_domain`; untagged posts are mapped from the description
   only when it has ≥2 cues for one category. Checked by hand on a random 60 (`evals/results/real_category_audit.json`):
   **0.7667 category accuracy, 0.85 persona-level** (single annotator, the author).
5. **Sampling**: up to 60 posts per in-market category plus 240 out-of-domain posts, seed 11 → **1,295 posts**
   (859 hourly, 423 fixed, 13 with no budget). Skill tags map to GigBid's vocabulary through `TAG_MAP`; the original tags stay in `upwork_skill_tags`.
6. **Contracts**: keep start dates 2015–2025; hourly = `hourly_rate > 0`; fixed = no hourly rate, paid > 0 and ended. Rates are clipped at
   $500/h and amounts at $100k before percentiles (p10–p90 per category).
7. **2024 posts**: 50k + 200k files merged, de-duplicated by link (733,655 unique posts), categorised by title, percentiles and weekly shares.

## What is real and what is synthetic, field by field

| Object | Real | Synthetic (and why) |
|---|---|---|
| Real job post | title, description (scrubbed), skill tags, budget type and amount, Connects, applicant band (→ midpoint), experience level, duration band, source URL | `industry` left empty; `duration_days` = 30 and Connects = 8–10 when the post does not state them (`_synthetic_fields` lists which) |
| Real client | country, payment verified, total spent, rating, review count (used as hires) | hidden preferences that GigSim's simulated client needs (generic-opening dislike, concise preference, budget flex, base reply), seeded by client id and marked `_hidden_source: synthetic` |
| Market stats | the `real` block of `/v1/market/stats` (contracts + 2024 posts) | the top-level p25–p90 (synthetic history; still used for synthetic jobs so all earlier results stay comparable) |
| Outcomes | – | every reply / hire is decided by GigSim's simulated client, for real and synthetic posts alike |
| Labels | – | real posts have **no** gold bid/scam/price labels; `_gold.requirements` is only the mapped skill tags |

How the system uses it: GigSim loads the real posts when `GIGSIM_REAL_JOBS=1` (on in the deployed demo) and lists the newest
posts first. For a real post the Pricing Strategist prices from the real contracts: an hourly rate inside the posted range for
hourly posts, a fixed amount from real fixed-contract percentiles otherwise, never below the user's floor
(`agent/nodes/pricing.py::quote_real`). Synthetic jobs keep the synthetic market so every earlier number is reproducible.

## What the real data showed

**1. The synthetic market is too generous for developers and too cheap for analysts.** Median hourly rate, synthetic
generator vs real contracts (`data/real/calibration.json`):

| Category | Synthetic | Real contracts p50 | Real n | Synthetic ÷ real |
|---|---|---|---|---|
| llm_apps | 55 | 32 | 1,873 | 1.72 |
| classical_ml | 45 | 39 | 1,793 | 1.15 |
| web_app | 40 | 25 | 13,304 | 1.6 |
| backend | 42 | 25 | 4,308 | 1.68 |
| mobile | 40 | 23 | 2,514 | 1.74 |
| ecommerce | 32 | 20 | 15,079 | 1.6 |
| bi | 32 | 40 | 3,640 | 0.8 |
| web_analytics | 28 | 46.8 | 3,361 | 0.6 |
| research | 28 | 40 | 318 | 0.7 |

Real fixed-price contracts are also small (llm_apps median $220, web_app $200). The synthetic world was not regenerated
(that would invalidate every labelled result); real posts use the real prices instead.

**2. The scam rules raised false alarms on real posts, so they were rewritten (v1 → v2).** v1 flagged any mention of
Telegram, WhatsApp, crypto or "for free". On real posts these are usually the *product* ("build a Telegram bot", "integrate
crypto payments"). v1 flagged 3.01% of the 1,295 board posts. Reading all 39 by hand found one that really dealt in off-platform payment
(a "USDT, BUSD and Payoneer seller wanted" post), two Telegram member-scraping jobs (spam rather than scams) and 36 false alarms. v2 needs an *ask* (contact me on X,
we pay in USDT, outside the platform, buy our kit). Results (`evals/results/real_scam_external.json`):

| | v1 | v2 |
|---|---|---|
| Synthetic scam jobs, text rules (780 jobs, 89 scams) | P 0.89, R 1.0 | P 1.0, R 1.0 |
| Synthetic injections (63) | P 1.0, R 1.0 | P 1.0, R 1.0 |
| Real board posts flagged (in-sample: v2 was written while reading these) | 3.01% | 0.08% |
| **3,000 held-out 2024 posts flagged** (different dataset, not read while writing v2) | 2.3% | **0.17%** |

The 5 v2 flags on the held-out posts, read by hand: one true positive (a client asking for a free trial video before
hiring), one ambiguous ("contact me via DM"), three false alarms ("feel free to contact me at any time", a product's "free
trial" feature, an "admin:" heading read as an injection). The cost: the v2 rules miss the "USDT seller" post that v1
caught by accident. Pipeline effect on the synthetic dev set: scam precision 0.9221 → 1.0 at recall 1.0, bid F1 0.9482 → 0.9526.

**3. Neither scam detector transfers across domains.** On the outside Fake-Job-Posting test half (general job ads, the
~10k template fakes removed), the freelance rules catch 0.3% of fakes. A TF-IDF + logistic-regression model trained on that
dataset's train half reaches F1 0.92 there, but catches **0 of the 71** synthetic freelance scams and flags 0.85% of real
Upwork posts. Scams in general job ads (fake employers, "earn $5000/week") and in freelance marketplaces (free work,
off-platform payment) look different, so the classifier is not shipped; the finding is reported instead.

**4. Real posts are harder to bid on.** In `pipeline_heuristic_real.json` (60 real posts, 15 in-market + 5 out-of-domain
per persona) the agents bid on 0.2889 of in-market posts and none of the out-of-domain ones. The main in-market skip
reasons are real-market facts the synthetic world under-represents: 30% of real clients have no verified payment method
(43% have never spent), and many fixed budgets or hourly ranges sit below the personas' floors ($30–45/h).

## Limitations

* **No real outcomes or labels.** Reply / hire rates on real posts come from GigSim's simulated clients with synthetic
  preferences; they say how the simulator reacts, not how real clients would.
* **Dated posts** (2023 for the board, 2022-07 to 2024-07 for prices). LLM-app rates in particular move fast.
* **Selection bias**: the 60k dataset was scraped from four searches (Developer, Marketing, 3D, Data science), so
  analyst and AI categories are thin (mlops 12, recsys 10 posts). Contract job titles were categorised by title alone,
  and the contracts dataset does not name its platform.
* **Category noise**: 23% of posts are in the wrong category and 15% are in the wrong persona's market (hand audit, n=60).
  The persona-level noise lowers the measured in-market bid rate.
* **Survivorship in contracts**: only awarded contracts are present, so prices for jobs that never hired are missing.
* **Template-heavy fake-job data**: 10,000 of 12,523 fakes share one template; results are reported with them removed.

```bash
uv pip install -e ".[data]"
python scripts/ingest_kaggle.py                                  # data/real/* (needs Kaggle access; anonymous download works)
python -m evals.runners.real_data_eval scam                      # evals/results/real_scam_external.json
GIGSIM_REAL_JOBS=1 uvicorn gigsim.server:app --port 8081 &       # then:
python -m evals.runners.real_data_eval pipeline                  # evals/results/pipeline_<profile>_real.json
```
